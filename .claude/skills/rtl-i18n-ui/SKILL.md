> Paths in this skill that start with `src/…`, `e2e/…` or `scripts/…` are relative to the web app, `apps/web/`, except in the "Mobile app" section, where they're relative to `apps/mobile/`. The React-free shared code (domain, shared schemas and sync rules, i18n config, messages) lives in `packages/core/` and is imported as `@qct/core/…`. Run `pnpm` scripts from the repo root.

# UI in this app: Arabic-first, RTL and LTR, phone-first

Users see Arabic, written right to left. English (`packages/core/messages/en.json`) is built, hidden and tested, so every screen must work in both directions without code changes. The main user is a teacher on an iPhone in the middle of a lesson: large tap targets, nothing that scrolls sideways, and it must keep working offline. The binding rules are in `BRIEF.md` §2 (i18n and direction) and §3 (the Arabic glossary).

## Text

- **Every user-facing string comes from `packages/core/messages/ar.json`** and its English twin `packages/core/messages/en.json`, with the same keys. That covers labels, buttons, empty states, toasts, aria-labels, `title`s and chart labels.
  - The test `packages/core/src/i18n/messages.test.ts` fails if the key sets differ or a message is empty.
  - Add the key to both files in the same change.
- **Use the glossary for domain terms.** `glossary.*` holds the brief's fixed vocabulary, for example `glossary.class` = الحلقة, `glossary.lesson` = الدرس, `glossary.memorizationRate` = تقييم الحفظ. Reuse those keys rather than writing a synonym, so wording stays consistent across screens.
- **Messages are ICU.** Use `{name}` placeholders and `plural`/`select`. Arabic plurals have six forms (`zero one two few many other`); write all the ones the sentence needs.
- **Rich text** (bold parts, inline icons) uses `t.rich("key", { b: (chunks) => <strong>{chunks}</strong> })` with tags in the message. Don't split a sentence across several keys, because word order differs between Arabic and English.
- **Errors are codes until the last moment.** Domain and schema code return codes (`packages/core/src/shared/schemas/errors.ts`, `packages/core/src/domain/quran/validation.ts`). Components turn them into text with `useErrorMessage()` (`src/i18n/use-error-message.ts`). Never put translated text in domain, server or schema code.
- **Wording:** neutral where possible, masculine when Arabic forces a choice (PLAN.md §0 #11). The tone is short and plain, as for a busy teacher.
- **shadcn/ui components** were generated with hardcoded English, such as "Close", "Loading" and the CommandDialog defaults. When you add or regenerate one, replace every English string with a translation or a required prop.

## Direction

- **Use logical Tailwind classes only:** `ms-/me-`, `ps-/pe-`, `start-/end-`, `text-start/text-end`, `border-s/border-e`, `rounded-s/rounded-e`, `inset-x-*`. `pnpm lint` fails on physical ones (`ml-`, `pr-`, `left-`, `text-right`, …). Vertical classes (`mt-`, `pb-`, `top-`) are fine.
- **Never write `dir="rtl"` or `dir="ltr"`.** Lint blocks it. `<html dir>` comes from `getDirection(locale)` (`packages/core/src/i18n/direction.ts`). Put `dir="auto"` on user-entered text (student names, notes, search input) so mixed Arabic and English displays correctly.
- **Icons that point somewhere** (back, next, chevrons, arrows) go through `<DirectionalIcon icon={ChevronLeft} />` (`src/components/directional-icon.tsx`). It mirrors them in RTL. Pick the icon as if for LTR: back = `ChevronLeft`/`ArrowLeft`, next = `ChevronRight`.
- **Sheets, drawers and popovers** use logical sides (`side="start"`/`"end"`). The shadcn `Sheet` here was changed from left/right to start/end; keep it that way.
- **Tables at 360 px** (see `month-table.tsx`): `table-fixed` with fixed widths for the date and number columns, so the text column wraps instead of widening the page. If you ever hide a table for screen readers only, put `sr-only` on a wrapping `div`: a `<table>` ignores the 1 px width.

## Numbers and dates

- **Format through next-intl** (`useFormatter()`, `format.dateTime`, `format.number`, `format.relativeTime`) with the named formats in `packages/core/src/i18n/formats.ts` (`lessonDate`, `weekday`, `month`, `average`, …). Add a named format rather than inline options. Never hardcode day or month names.
- **The Arabic locale tag is `ar-u-ca-gregory-nu-latn`** (`getIntlLocale` in `packages/core/src/i18n/config.ts`): Western digits and the Gregorian calendar, per the brief.
- **Lesson dates are calendar dates** (`LocalDate`, `YYYY-MM-DD`), not instants. Format them via `localDateToUtcDate` with formats that set `timeZone: "UTC"` (see `use-lesson-date.ts`), or the day shifts with the device time zone. "Today" comes from the tenant's time zone: `todayInTimeZone(session.timezone)`.
- **Numeric inputs accept Arabic-Indic digits.** Parse with `parseIntegerInput` / `toWesternDigits` (`packages/core/src/domain/text/digits.ts`). Use `inputMode="numeric"` for the phone keypad.
- **Sort names** with `Intl.Collator(locale)`.

## Layout for an iPhone mid-lesson

- **Design for 360 px first,** then let it grow. Nothing may scroll sideways: `<main>` has `overflow-x-clip` as a guard, but don't rely on it.
- **Tap targets are at least 44 px** (`h-11`/`size-11`). Frequent actions such as score buttons and attendance toggles are larger.
- **When a component sits in variable-width containers,** use container queries (`@container` on the card, `@lg:grid-cols-2` inside) rather than viewport breakpoints. Score grids once shrank to 32 px at 1024 px with viewport breakpoints.
- **Keep busy screens calm.** The user found a screen full of number buttons dizzying. Prefer the platform's own picker for a choice among many values: a native `<select>`, which iPhone shows as a wheel (see `ScorePicker`). Show lists of items as collapsible sections whose closed row says what matters (see `HomeworkItem` in `student-today.tsx`).
- **The shell pads for the notch and home indicator** with `env(safe-area-inset-*)` (`app-shell.tsx`). New fixed or sticky bars must do the same.
- **Long Arabic names truncate.** Give the important text its own line rather than letting badges squeeze it to a few letters.
- **Feedback after a tap must be instant.** Writes go to IndexedDB and are usually fast, but WebKit took about 250 ms. For high-frequency controls, show the new state optimistically, as `ScorePicker` does. See the `offline-sync-data` skill for the write path.
- **Hide what the user may not do.** Gate actions with `useAccess()` (`can("lessons.run")`, `isAdmin`…, from `src/client/access.ts`). For a read-only view of a form, wrap its controls in `<fieldset disabled>`, keeping navigation (tabs, links, expand toggles) outside it. A drawer or dialog opened from inside renders in a portal, outside the fieldset, so its controls stay enabled: don't open it at all (as `MonthTable` does with `editable`). The server enforces access anyway; this is for a clear UI.
- **Printing** goes through the browser, not a PDF library (Arabic shaping and order stay exact, and it works offline): `/print` in its own route group (`src/app/(print)`, without the app shell), A4 sheets with fixed light colours (`MonthSheet`), and the print CSS at the end of `globals.css` (`@page` A4 with no margin, a page per `.print-page`, `print-color-adjust: exact`). Hide screen-only parts with `print:hidden`. Don't rely on `@page`: iOS prints on its own paper (US Letter in some regions) with its own margins, so never force a sheet to a full page's height. Check a change with Chromium's `page.pdf({ preferCSSPageSize: true })`, also after adding `@page { size: letter; margin: 12mm !important; }`, and count the pages.
- **Pages must not depend on the server for content.** Routes are `?id=` query pages served from the service-worker cache, and data comes from Dexie. Never fetch data in a server component.

## Mobile app (`apps/mobile`, Expo / React Native)

The same product rules apply (messages, glossary, wording, 360 px, offline). What differs:

- **Expo changes every SDK.** Before using an Expo, Expo Router or React Native API, check the docs for the installed SDK (`https://docs.expo.dev/versions/v58.0.0/` for SDK 58), not memory. Add libraries with `pnpm exec expo install <pkg>` from `apps/mobile`, so they get the SDK's versions. `expo-doctor` must pass (TypeScript is excluded on purpose: the workspace stays on one version).
- **Native controls first** (PLAN.md §0 #44): native stack and tabs (`expo-router`, `expo-router/native-tabs`), the native picker wheel for marks, the system date picker, form sheets, native menus, alerts, the header search bar and the share sheet. Content (cards, lists, the month table) is React Native core components in the shared theme. Don't rebuild with JavaScript what the platform has.
- **Direction is fixed when the app starts** (§0 #53). The `expo-localization` plugin (`forcesRTL`) starts it in RTL, and a change of language reloads the app. Native headers, tabs and back buttons mirror themselves.
- **On iOS, UIKit's own views take their direction from the app's localization, not from `forcesRTL`.** That covers the native header and large titles. The app declares Arabic as its only localization (`supportedLocales: ["ar"]` in the `expo-localization` plugin, `CFBundleDevelopmentRegion: "ar"`). Without that, iOS treated it as an English app and put the large title on the left. Enabling English later means adding `en` there, and the language switch must keep UIKit and React Native in step. Native config changes need a new build.
- **No large titles** (`headerLargeTitle`). In RTL, react-native-screens forces right-to-left on the navigation bar's subviews, and the large title, which iOS already mirrors, came out flipped twice: on the left, with mirrored glyphs. Standard titles are centred and fine.
- **Header actions are `Stack.Toolbar`** (placement `"right"`, which is the trailing side in RTL): `Stack.Toolbar.Button` and `Stack.Toolbar.Menu` with `MenuAction`s (`destructive` for archive). Give each an `accessibilityLabel` and a text label. Get icons from `useToolbarIcon(sf, md)` (`src/components/icons.tsx`): an SF Symbol on iOS, the Material symbol drawn to an image on Android, which accepts only images there (needs `@expo/ui`). For a row's "opens a page" chevron, use `Chevron`, which picks left or right by direction.
- **Forms open over the tabs as root-stack routes.** Short ones are form sheets sized to their content (`formSheet` in the root layout, with the body in `Sheet`); long ones are page sheets with a native header (`presentation: "modal"`). Confirm destructive one-step actions with `Alert.alert`. Choices among many values use `PickerField` (the native picker); a few options use `ChoiceList` (radio rows). A page reachable from two tabs gets a route file in each stack that re-exports a screen from `src/screens/`.
- **Marks use `ScorePicker`** (the native picker: a short wheel on iOS, a dropdown on Android) and show the chosen mark before the write lands. A searchable list in a sheet (the sura picker) is React Native's `Modal` with `presentationStyle="pageSheet"`, so its state stays in the form. A form on its own route can't call back into the screen that opened it; use a small event like `src/data/homework-events.ts`.
- **A paragraph that starts with Latin text** (a user name) takes a left-to-right base direction on Android, and its punctuation moves to the wrong side. Put the name on its own line, or start the sentence with Arabic.
- **Every `Alert.alert` passes its own buttons**: with none, Android shows an English "OK". A message alone gets `[{ text: t("common.close") }]`.
- **The theme** is the user's choice in Settings, applied with `Appearance.setColorScheme` (`src/theme/preference.ts`); `useTheme()` and the native headers follow it, so never read the system scheme directly.
- **Printing on mobile** goes through `usePrintSheets()` (`src/print/use-print.ts`): the shared sheet data laid out as HTML (`src/print/month-sheet-html.ts`, which mirrors the web's `MonthSheet`: change both together), the font embedded, then `expo-print` or a shared PDF. User text in that HTML goes through its `bdi()` helper, which escapes it. QR codes use `qrShape` from `@qct/core/shared/qr` (the app's `QrCode` component, or `qrSvgMarkup` in HTML), always black on white.
- **Tablets:** give each `Screen` the web container's width (`width="page" | "narrow" | "form"`, 896 / 672 / 448 dp); lists of cards that the web shows in columns go in `Grid` (`maxColumns`, at the web's 768 and 1280 breakpoints, from the window width). Phones are locked to portrait at start; tablets turn, so check a layout in both orientations on `qct_tablet`.
- **Two numbers on one line can reorder in RTL** ("2015 · 11 سنة"). Give each its own line, or wrap the line in an LTR `writingDirection`.
- **Styles are logical only:** `marginStart`/`marginEnd`, `paddingStart`/`paddingEnd`, `start`/`end`, `borderStartWidth`, `borderTopStartRadius`, `marginHorizontal`. `pnpm lint` blocks `marginLeft`, `paddingRight`, `left`, `right`, `borderLeft*` and `textAlign: "left" | "right"`. Text aligns with its writing direction by itself, and centring is fine.
- **Text goes through `Text`** (`src/components/text.tsx`): the locale's font (IBM Plex Sans Arabic or IBM Plex Sans, loaded at start from `src/theme/fonts.ts`) and the theme's colors. A custom font has one family per weight, so use its `weight` prop, never `fontWeight`. `Text` also sets `textBreakStrategy="simple"`: with Android's default, Arabic in the custom font lost its last word to a clipped second line. A raw `<Text>` from React Native skips that fix, so don't use it. It still isn't enough for a label sized to its own text: Android can lay it out a fraction of a pixel narrower than it measured it, depending on where it sits, and then breaks the word itself ("اختبار" showed as "اختبا"). `fontWeight` doesn't fix it (tried in 2.9). Give such labels the full width of their control (`alignSelf: "stretch"` with `textAlign: "center"`, as `Button` does), equal-width siblings, a minimum width (`SmallButton`), or, for a badge, `Badge`, which pads its label with figure spaces. Check new short labels on the emulator.
- **Every screen body is a `Screen`** (`src/components/screen.tsx`). It handles insets: the system's on iOS, the gesture bar on edge-to-edge Android. It also keeps the field being typed in above the keyboard on both platforms (`react-native-keyboard-controller`, whose `KeyboardProvider` wraps the root layout). Forms use `TextField`, `Button` and `FormError` (`src/components/`): labelled fields at least 48 pt tall, errors as text from the messages.
- **Colors** come from `useTheme()` (`src/theme/theme.ts`), light or dark following the phone. `src/theme/colors.ts` mirrors the web's `globals.css` tokens converted from OKLCH to hex; change both together. Native headers and tabs get the same colors and fonts through `navigationTheme()` and `useStackOptions()`.
- **Messages and formats** use `use-intl` (`useTranslations`, `useFormatter`) with the same keys and named formats, through `AppIntlProvider` (`src/i18n/intl-provider.tsx`).
- **Hermes lacks parts of `Intl`:** `PluralRules`, `Locale`, `RelativeTimeFormat` and `supportedValuesOf`, plus `crypto.getRandomValues`. `src/polyfills.ts` loads them first (from `index.ts`), with `ar` and `en` data; a new locale needs its data files there. Never use `Intl.Locale` directly; `languageOf()` in `packages/core/src/i18n/direction.ts` parses a tag. Development builds show an Intl check in Settings for a quick look on a device.
- **Tests:** Jest with `jest-expo` and Testing Library (`render` and `fireEvent` are async: `await render(…)`, `await fireEvent.changeText(…)`; without the await, a tap runs before the typed text reaches state), wrapped in `AppIntlProvider` with the real Arabic messages. A screen that uses the local data renders with `renderWithApp` (`src/test/app-services.tsx`): the real store and sync engine over core's memory adapter. `jest.setup.ts` mocks the native edges (the auth client, the database file, network and app state). An ES-module-only package needs adding to `transformIgnorePatterns` in `apps/mobile/package.json`. Screens that use navigation mock `expo-router` with `jest.mock("expo-router", () => jest.requireActual("@/test/expo-router-mock"))`, which renders toolbar items and the header search bar as plain controls. Never put a test (or any non-route file) under `src/app/`: Expo Router bundles every file there as a route, and Testing Library breaks the app bundle.
- **Looking at it:** the Android emulator `qct_phone` (360 dp) with `pnpm mobile:android`; the user checks the iPhone development build (`eas build --profile development --platform ios`). Check Arabic, light and dark. uiautomator doesn't see inside Android modals and sheets, so drive those by coordinates from a screenshot, and never press BACK to hide a keyboard that isn't open (it closes the sheet). On Windows, Metro's watcher sometimes misses an edit: if a change doesn't show, restart it with `pnpm exec expo start --dev-client --clear` (from `apps/mobile`) and reopen the app.

## Checking your change

1. `pnpm lint && pnpm typecheck && pnpm test`. These catch physical classes, literal `dir`, and missing or empty message keys.
2. Component tests: `// @vitest-environment jsdom`, then `renderArabic(<X />)` from `src/test/dom.tsx` (real Arabic messages, RTL). Query by role and accessible name in Arabic, taken from the message files.
3. Look at it in a browser at 360 px in Arabic, and quickly in English as well:
   - A user whose `locale` is `en` gets English once `ENABLED_LOCALES=ar,en` is set.
   - `pnpm test:e2e` runs an LTR smoke test that checks `dir`, `lang` and no horizontal overflow on every main screen.
   - See the `plan-step-workflow` skill for ports and accounts.
4. In the mobile app: Jest tests render with `renderWithApp(ui, services)` (`apps/mobile/src/test/app-services.tsx`, Arabic by default; a third argument picks `en`). `src/ltr.test.tsx` renders the main screens in English and fails on any Arabic text or label left on them: add a new main screen there. Then check it on the emulator at 360 dp; `pnpm mobile:e2e` runs the Maestro flows (see `plan-step-workflow`).
