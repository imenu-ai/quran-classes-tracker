# Android builds, the local emulator and Google Play releases

## What this file is for

This is the step-by-step guide for running and shipping the Android version of the mobile app (`apps/mobile`). Follow it whenever you need to:

- start the **Android emulator** on this PC and run the app on it with live code from Metro (the everyday development loop);
- try a **release-like build** on the emulator before shipping;
- make a **production build** and send it to **Google Play**;
- make an **APK** for people who install it outside Google Play;
- send a **JavaScript-only fix** to installed apps (EAS Update).

Android builds can be made in two places:

- **On this PC** with Gradle, through `expo run:android`. This is the fast loop for the emulator.
- **In the cloud** with EAS Build. This is how store builds and APKs are made.

Run `pnpm …` commands from the **repo root** and `npx eas-cli …` and `pnpm exec expo …` commands from **`apps/mobile`**:

```powershell
cd C:\Users\mhmdt\imenu\quran-classes-tracker            # pnpm scripts
cd C:\Users\mhmdt\imenu\quran-classes-tracker\apps\mobile # eas-cli and expo
```

The iPhone guide is in [ios-builds.md](ios-builds.md). Play's listing, App content and Data safety answers, graphics and release notes are in [../store/play-store.md](../store/play-store.md) and [../store/play/](../store/play/).

## Once per computer: the Windows setup

This is already done on this PC (October 2026). Check it again after reinstalling Windows or Android Studio.

1. **Android Studio**, with the SDK at `%LOCALAPPDATA%\Android\Sdk`. Under SDK Manager, have:
   - Android SDK Platform 36;
   - Build-Tools 36;
   - Platform-Tools;
   - Emulator;
   - NDK and CMake 3.22.1, which the first build downloads by itself if they're missing.
2. **JDK 17** (Microsoft OpenJDK 17), with `JAVA_HOME` set as a user variable.
3. **Environment variables** (user level):
   - `ANDROID_HOME` = `%LOCALAPPDATA%\Android\Sdk`;
   - `Path` includes `%ANDROID_HOME%\platform-tools` and `%ANDROID_HOME%\emulator`.

   Check them in a **new** terminal:

   ```powershell
   adb version
   emulator -list-avds
   java -version        # 17
   ```

4. **Windows long paths.** The React Native build's paths go past 260 characters. In an admin PowerShell:

   ```powershell
   New-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Control\FileSystem" -Name LongPathsEnabled -Value 1 -PropertyType DWORD -Force
   ```

5. **ninja 1.12 or later in CMake.** The ninja 1.10.2 that ships with CMake 3.22.1 fails on long paths ("Filename longer than 260 characters").
   1. Download `ninja-win.zip` from the ninja-build GitHub releases.
   2. Rename `%LOCALAPPDATA%\Android\Sdk\cmake\3.22.1\bin\ninja.exe` to `ninja-1.10.2.exe`.
   3. Put the new `ninja.exe` in its place.

   An SDK update can bring the old one back, so repeat this if the error returns.

6. **Dependencies:** `pnpm install` from the repo root.
7. **Expo account** for the cloud builds: `npx eas-cli login`, then `npx eas-cli whoami` shows you and the `imenu` organization.

## A. The emulators

There are two emulators (AVDs). Run **one at a time**, because the PC has 16 GB of RAM.

| AVD          | Device                                    | Size                                    | Used for                                                    |
| ------------ | ----------------------------------------- | --------------------------------------- | ----------------------------------------------------------- |
| `qct_phone`  | Small Phone, API 36, Google Play, x86_64  | 720 × 1280 at 320 dpi = **360 dp** wide | Everyday checks (the app's narrowest target), Maestro flows |
| `qct_tablet` | Pixel Tablet, API 36, Google Play, x86_64 | 2560 × 1600 at 320 dpi                  | Tablet layouts; it rotates                                  |

If one is missing, create it in Android Studio → **Device Manager** → **+** → Create Virtual Device:

1. Choose the device (Phone → "Small Phone", or Tablet → "Pixel Tablet").
2. Choose the API 36 image with **Google Play**, x86_64.
3. Name it as in the table.

### A1. Start one

```powershell
emulator -avd qct_phone -no-snapshot-save
```

The window appears and boots in about a minute; leave that terminal open. If `emulator` isn't found, use the full path: `& "$env:LOCALAPPDATA\Android\Sdk\emulator\emulator.exe" -avd qct_phone`. Android Studio's Device Manager (▶ button) works too.

In a second terminal, wait until it has booted:

```powershell
adb wait-for-device
adb shell getprop sys.boot_completed   # prints 1 when it's ready
adb devices                            # emulator-5554   device
```

### A2. Stop it

```powershell
adb emu kill
```

## B. Run the app on the emulator (development)

This builds the **dev client** on this PC, installs it, and loads the app's JavaScript from Metro, so code changes show up in a second.

### B1. Point the app at a server

The app reads `EXPO_PUBLIC_API_URL` when Metro starts. `apps/mobile/.env.local` takes precedence over `apps/mobile/.env`; create it from the example if it's missing:

```powershell
cd C:\Users\mhmdt\imenu\quran-classes-tracker\apps\mobile
Copy-Item .env.example .env.local
```

For your local web app (`pnpm dev` on port 3000), keep `EXPO_PUBLIC_API_URL=http://localhost:3000`. The emulator then reaches the PC's port 3000 through `adb reverse`, which step B2 sets up.

To use production instead, set `https://quran.imenu.ai` (real data, careful).

### B2. First run, or after a native change

1. Start the emulator (A1).
2. Start the web app in its own terminal, from the repo root: `pnpm dev`.
3. Forward the web app's port into the emulator:

   ```powershell
   adb reverse tcp:3000 tcp:3000
   ```

4. Build, install and start Metro, from the repo root:

   ```powershell
   pnpm mobile:android
   ```

   This runs `expo run:android`. It generates `apps/mobile/android`, builds a debug APK with Gradle, installs it on the running emulator, starts Metro on port 8081 and opens the app.
   - The **first** build takes 10–20 minutes, because Gradle and the NDK download once.
   - Later builds take about a minute.

### B3. Every day after that

1. Start the emulator (A1).
2. Start the web app in its own terminal (`pnpm dev`).
3. Forward the ports. Forwarding is lost when the emulator restarts:

   ```powershell
   adb reverse tcp:3000 tcp:3000
   adb reverse tcp:8081 tcp:8081
   ```

4. Start Metro, from the repo root:

   ```powershell
   pnpm mobile
   ```

5. Open the app on the emulator. You can also press **`a`** in the Metro terminal to open it there.

Press **`r`** in the Metro terminal to reload, and **`m`** for the developer menu.

### B4. When you need a new build

Metro reloads JavaScript only. Run `pnpm mobile:android` again after:

- installing a native library;
- changing `app.json` or `plugins/`;
- an Expo SDK upgrade;
- pulling such a change from git.

If a native build behaves strangely, start from a clean native project:

```powershell
Remove-Item -Recurse -Force C:\Users\mhmdt\imenu\quran-classes-tracker\apps\mobile\android
pnpm mobile:android
```

It's safe: the folder is generated and gitignored.

### B5. The tablet

The steps are the same with `qct_tablet`. Stop the phone first (`adb emu kill`), start the tablet, and run B3. The development app has to be installed on each emulator once, with `pnpm mobile:android`. Turn the tablet with the rotate buttons beside the emulator window and check both orientations.

### B6. The Maestro flows

The end-to-end flows (`pnpm mobile:e2e`) need this development build on the running emulator. They start their own web server and Metro (port 8082), so stop `pnpm mobile` first. See the README, "End-to-end flows (Maestro, Android)".

## C. A release-like build on the emulator

The development build loads its code from Metro. Before shipping, try the app the way users get it, with the JavaScript inside the build and no developer tools. There are two ways:

### C1. A local release build (fast, your server)

From `apps/mobile`:

```powershell
pnpm exec expo run:android --variant release
```

- The JavaScript is bundled into the APK with `EXPO_PUBLIC_API_URL` as it is in `.env.local` **at build time**.
- It's signed with the local debug key and replaces the development app on the emulator.
- Run `pnpm mobile:android` afterwards to get the development app back.

### C2. The real store build as an APK (EAS, production server)

From `apps/mobile`:

```powershell
npx eas-cli build --profile android-apk --platform android
```

When it's done (10–30 minutes), with the emulator running:

```powershell
adb uninstall ai.imenu.quran                        # the local build has a different signing key
npx eas-cli build:run --platform android --latest   # downloads the APK and installs it
```

- `adb uninstall` removes the app's data on the emulator; that's fine for a test device.
- If you skip it, the install fails with `INSTALL_FAILED_UPDATE_INCOMPATIBLE`.
- This build talks to **production**: sign in with the demo center.
- Afterwards, run `adb uninstall ai.imenu.quran`, then `pnpm mobile:android`, to go back to the development app.

### C3. A cloud dev client (no local toolchain)

If the local Gradle build is broken and you just need the dev client:

```powershell
npx eas-cli build --profile development --platform android
npx eas-cli build:run --platform android --latest
```

Then run B3 as usual.

## D. A production build for Google Play

### D1. Before you build (every release)

1. **The code is ready.** From the repo root, `pnpm lint && pnpm typecheck && pnpm test` pass, the Maestro flows pass (`pnpm mobile:e2e`), and the app was tried as a release build (C).
2. **The web app is deployed first.** The build talks to `https://quran.imenu.ai`. Play's reviewers open the `/privacy` and `/support` pages, including the account deletion section.
3. **Bump the version** in **both** `apps/mobile/app.json` and `apps/mobile/package.json`, for example `1.1.0` → `1.2.0`.
   - iOS and Android share this version. Bump it once per release and build both.
   - The version code goes up by itself on EAS.
4. **Write the release notes** in [../store/play-store.md](../store/play-store.md), in Play's `<ar>` / `<en-US>` format, at most 500 characters per language.
5. **Commit, and build from a clean tree.** EAS uploads the project without what's in `.gitignore`, so `.env.local` and `android/` stay behind.

### D2. Build

From `apps/mobile`:

```powershell
npx eas-cli build --profile production --platform android
```

The result is an `.aab` (Android App Bundle), and the build page shows its version and version code.

**Keystore warning:** EAS already holds the app's upload key, created by the first build. If EAS ever asks **"Generate a new Android Keystore?"** for this app, **stop**.

- A build signed with a new key can't be uploaded as an update to the Play app.
- To see the key, run `npx eas-cli credentials` → Android → `ai.imenu.quran` → production.
- If it's really lost, the Play Console can reset the upload key: Test and release → App integrity → App signing → "Request upload key reset".

### D3. Send it to Google Play

You can send the build in one of two ways.

#### Option 1: automatically with EAS Submit

Set up a Google service account once:

1. In the [Google Cloud console](https://console.cloud.google.com/):
   1. Create (or pick) a project.
   2. Enable the **Google Play Android Developer API**.
   3. Go to IAM & Admin → Service accounts → **Create service account**. It needs no roles.
   4. Open the account → Keys → **Add key** → JSON, and download the file. Keep it out of the repo.
2. In the [Play Console](https://play.google.com/console):
   1. Go to **Users and permissions** → Invite new users, and enter the service account's email.
   2. Give it access to this app with the release permissions ("Release to production, exclude devices, and use Play App Signing", and "Release apps to testing tracks").
   3. Click **Invite user**.
3. Give the key to EAS. Run `npx eas-cli credentials` → Android → `ai.imenu.quran` → **Google Service Account** → upload the JSON key.

After that, each release:

```powershell
npx eas-cli submit --profile production --platform android --latest
```

This uploads the newest Android build to the **internal testing** track, which is EAS's default.

To aim at another track by default, add this to `eas.json` under `submit.production`:

```json
"android": { "track": "internal" }
```

The track can be `internal`, `alpha` (closed), `beta` (open) or `production`.

To build and submit in one go, add `--auto-submit` to the build command in D2.

#### Option 2: by hand

1. Download the `.aab`: expo.dev → the project → Builds → the build → **Download**.
2. In the Play Console, open the app and go to **Test and release** → **Testing** → **Internal testing**. Click **Create new release**.
3. Upload the `.aab`. Its version code must be higher than every earlier upload.
4. Paste the release notes (the `<ar>…</ar><en-US>…</en-US>` block from `play-store.md`). Click **Next**, then **Save and publish** (or "Review release" → "Start rollout").

### D4. Test, then release to production

1. **Install from internal testing.** On a phone signed in with a tester account, open the internal test's opt-in link (Internal testing → Testers → "Copy link"). Install the app from Play and run through the main flow.
2. **Promote it.** Go to Internal testing → the release → **Promote release** → **Production**. Check the release notes, then **Start rollout to Production**.

   You can start with a staged rollout (for example 20%) and raise it later from Production → Releases.

3. **Wait for review.** It usually takes a few hours to a few days. The Play Console's **Publishing overview** shows the status. If **Managed publishing** is on, you press "Publish" yourself after approval.

A new **personal** developer account must first run a closed test with at least 12 testers for 14 days in a row before production. This app is already published, so that requirement no longer applies to it.

## E. An APK without Google Play

For people who install the app directly:

```powershell
npx eas-cli build --profile android-apk --platform android
```

1. The command prints a link to the build page. Send that link.
2. People open it on their phone, download the APK, and allow installing from that source when Android asks. Play Protect may warn about an unknown developer.
3. JavaScript fixes reach it through EAS Update (F), like the store app. Native changes need a new APK.

**APK copies and Play copies can't update each other.** The APK is signed with EAS's key. Google Play re-signs the store version with Google's own app signing key, unless the app was set up to use the upload key; you can compare the two certificates under Play Console → Test and release → App integrity → App signing. When the keys differ:

- A phone with the APK can't move to the Play version without uninstalling.
- Uninstalling deletes the app's data, so make sure everything has synced first: the sync indicator shows no pending changes.

## F. JavaScript-only fixes (EAS Update)

From `apps/mobile`:

```powershell
npx eas-cli update --channel production --message "fix: …" --platform android
```

- Leave out `--platform android` to publish for iOS and Android together.
- It reaches only builds with the **same app version** (the runtime version follows it).
- The app downloads the update when it starts and uses it from the next start.
- To undo a bad update, see expo.dev → the project → Updates, or republish an earlier one with `npx eas-cli update:republish`.
- Never use it for a change that needs a newer server unless the web app is deployed first.

## Troubleshooting

| Problem                                                                    | Fix                                                                                                                                                                                                                                                               |
| -------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `adb devices` shows the emulator as **`offline`**, or hangs                | End every adb (`taskkill /F /IM adb.exe`), then `adb start-server`. Still offline? Close the emulator and cold-boot it: `emulator -avd qct_phone -no-snapshot-load`. Last resort: Device Manager → the AVD → ⋮ → **Wipe Data** (the app must be installed again). |
| Build fails with "Filename longer than 260 characters"                     | ninja is back to 1.10.2 (setup step 5), or long paths are off (step 4).                                                                                                                                                                                           |
| The app shows "Unable to load script" or can't find Metro                  | `adb reverse tcp:8081 tcp:8081`, and check that `pnpm mobile` is running.                                                                                                                                                                                         |
| Sign-in says there's no connection                                         | `adb reverse tcp:3000 tcp:3000`, check that `pnpm dev` is running and `.env.local` says `http://localhost:3000`, then restart Metro with `pnpm exec expo start --dev-client --clear` (from `apps/mobile`).                                                        |
| A code change doesn't show                                                 | Metro's watcher missed it on Windows: restart Metro with `--clear` (as above) and reopen the app.                                                                                                                                                                 |
| The emulator shows its home screen and the app was killed at start ("ANR") | The emulator has run too long: `adb reboot`, then open the app again.                                                                                                                                                                                             |
| `INSTALL_FAILED_UPDATE_INCOMPATIBLE`                                       | The installed app has another signing key: `adb uninstall ai.imenu.quran` (deletes its data on that device), then install again.                                                                                                                                  |
| Strange Expo CLI errors after many `pnpm add`s (for example in `chalk`)    | Reinstall cleanly from the repo root: delete `node_modules` and run `pnpm install --frozen-lockfile`.                                                                                                                                                             |
| Play rejects the upload: "Version code … has already been used"            | That build was already uploaded. Build again with D2 (EAS raises the code), or use the existing upload.                                                                                                                                                           |
| Play rejects the upload: wrong signing key                                 | The build wasn't signed with the app's upload key: see the keystore warning in D2.                                                                                                                                                                                |
